# F26 Wi-Fi and packet-transmission review

Date: 2026-09-06. Based on the F25 source delivered in this conversation, which already contains the UI and lifecycle fixes from the F24 upload. Version: `5.0.2-f26`, code `7`.

## Findings and corrections

| Confirmed source issue | Correction in F26 | Relevance to jitter or reliability |
| --- | --- | --- |
| Starting the gameplay monitor called its stop/reset routine **after** remembering the verified connection. This erased the identity and made the next monitor tick reconnect a healthy socket. | Reset the old monitor first, then remember the socket actually used by the successful startup probe. | Removes an unnecessary startup-adjacent interruption. |
| Network identity included every link address, in their supplied order. IPv6 address changes could therefore reconnect the IPv4 tunnel. | Identity uses the Android Network, locked interface, and actual source IPv4. Unrelated addresses, DNS, RSSI, and validation changes do not trigger a bind. | Removes an avoidable reconnect trigger. No phone trace has yet correlated this trigger with a reported jitter event. |
| An unavailable station Network could be reported as a healthy hotspot path solely because an interface index/IP remained saved. The preferred stored Network was also accepted without checking that it still carried the locked IPv4. | Keep the session's LAN selection independent of mutable discovery state; check the exact source/interface. Kernel fallback requires an original path without an Android Network and a live matching interface/IP/index. | Prevents false recovery and selection of a stale source. Non-Wi-Fi candidates are excluded from gameplay path selection. |
| `onLost` tried to infer which Network disappeared by querying current connectivity state; `onAvailable` could run before its link addresses were ready. Cooldown skips had no precisely scheduled retry. | Compare loss against the remembered bound Network; process copied LinkProperties through one executor; protect callbacks against shutdown; retry failed binds using elapsed realtime. A new exact Network can recover without waiting for an old failed candidate's cooldown. | Addresses callback ordering and recovery delays. Real Android callback execution remains untested here. |
| Native startup/rebind ignored a false preparation callback whenever a configured source IP existed. The false result could represent failed VPN protection or failed Android binding, not just a legitimate hotspot owner. | Treat preparation as mandatory. Kotlin explicitly accepts a verified live hotspot source path. Native owns/closes the callback descriptor; Kotlin borrows a duplicate, including on exceptions. A failed rebind attempts to restore connected mode but still reports failure. | Avoids silently proceeding on an unprotected or incorrectly bound socket. |
| The native listener bound to the **peer's** advertised destination port. A vanished source bind could fall back to a wildcard. | Separate local advertised port from peer destination port through Kotlin/JNI/C++; validate ports and require the configured source bind. Stop allowing duplicate unicast listeners with SO_REUSEADDR. | Fixes connections with asymmetric advertised ports and prevents silent source changes or datagram sharing with an overlapping listener. |
| An asynchronous socket error could leave POLLERR asserted after the extended error queue was empty. The receive loop would immediately poll again. | Drain a bounded number of extended notifications, then consume SO_ERROR as well. | Local loopback regression demonstrates that error readiness clears instead of leaving the receive loop spinning. |
| TX diagnostics retained outgoing packet data in the kernel error queue, sharing the socket receive-memory budget. The reader treated a zero-byte diagnostic payload as completion. | Request SOF_TIMESTAMPING_OPT_TSONLY and parse ancillary timestamps even with a zero-byte payload. Align ancillary buffers and size the receive buffer for both supported timestamp records. | Reduces diagnostic memory charged to the receive budget; host tests verify both timestamp stages. No on-device CPU or memory reduction is claimed. |
| Native socket writes lacked MSG_NOSIGNAL; closing the bridge peer could raise SIGPIPE. Packet-oriented writes also contained stream-style partial-write continuation. | Suppress SIGPIPE, use nonblocking datagram operations, require successful nonblocking setup, reject truncated receives, and fail an unexpected short packet write without emitting its suffix as another packet. | Prevents process termination on bridge closure and hardens packet boundaries. |
| The service polled packet counts but had no indication that native workers had cancelled themselves after a fatal input failure. | Append a native liveness field to the stats array and close the VPN session with a reconnect message if workers stop unexpectedly. | Prevents an indefinitely “connected” app backed by stopped packet workers. The service reaction is source-checked; Android execution is pending. |
| IPv6 UDP passthrough created an unconnected channel but its input loop used `read()`, which requires a connected channel. The cache key omitted the remote endpoint, and binding the proxy to the game's source port could collide with another socket. | A shared protected socket factory connects IPv4/IPv6 proxy channels before use. Each proxy uses an OS-assigned port and retains the original endpoint mapping; IPv6 cache keys include both endpoints. | Fixes IPv6 replies and incorrect reuse across remote destinations. Actual JVM IPv4/IPv6 loopback round trips pass. |
| UDP/TCP output exceptions could bypass returning a pooled packet. Failed UDP registration could leave an open socket; a failed input could leave an open cache entry with no receive registration. | Return pooled packets in `finally`; close incomplete socket creations/registrations; close unusable input channels so they can be recreated. Transient PortUnreachableException preserves the existing UDP port. | Bounds avoidable resource/allocation pressure during repeated networking failures. No Android GC benchmark was performed. |

The packet classifier, game payload contents, score decoder, and PeerLink tunnel header remain unchanged. The 1400-byte TUN MTU plus 56-byte tunnel header, 8-byte UDP header and 20-byte IPv4 header is 1484 bytes on a standard 1500-byte path. This arithmetic does not prove every hotspot has that path MTU. Full raw packet-file capture remains disabled; inherited bounded match telemetry and timing metadata remain enabled.

## Verification

Run `python3 tests/run_checks.py` with Python 3, g++, and JDK 17 or later. The runner checks that application source hashes are unchanged by tests.

- **105 native checks:** 51 retained packet/routing checks, 16 F25 lifecycle/trace checks, and 38 F26 socket/liveness checks. Production C++ is compiled with AddressSanitizer and UndefinedBehaviorSanitizer. The new socket suite exercises real local IPv4 UDP and UNIX sockets, independent ports, rebind failures/exceptions, FD ownership, shutdown, pending socket errors, payload-free TX timestamps, truncation, empty UDP, bridge closure, and 64 full-MTU frames during concurrent TX/reconnect transactions.
- **35 executed JVM checks:** 17 against the production gameplay-path policy and 18 against the production IPv4/IPv6 socket factory, including loopback round trips and error cleanup.
- **Source/ABI checks:** Kotlin structure, manifest/resources, exact nativeStart argument types across Kotlin/C++ header/implementation, monitor initialization ordering, callback ownership, liveness propagation, and packet-pool cleanup. Retained discovery/Prime/trace/reference suites also pass.
- Current stage results and output logs are in `verification/`. All 22 stages must succeed. These stages and individual checks are different counts.

Android/JNI adapters in the native harness are mocks. The concurrent reconnect test exercises real UDP disconnect/connect and native synchronization, but its Android protect/bind callback is a no-op mock. It does **not** simulate Wi-Fi radio roaming. The JVM tests compile and execute the two Java production helpers; they do **not** compile the Android Kotlin application.

LeakSanitizer remains disabled because the supplied environment cannot enumerate process threads; ASan and UBSan remain enabled. ThreadSanitizer was not run.

The Android SDK/build dependencies were unavailable in the editing environment. No F26 APK or Android build result is supplied, and no phone, emulator, UI render, or gameplay latency measurement was performed. The included workflow builds the assembled project and runs Android unit tests; it has not been run against a connected repository in this session.

## Required device checks

1. Build F26 and install it on both phones. Test both two-phone hotspot roles and a shared third-device Wi-Fi network, with cellular enabled and disabled as appropriate for the game's Internet needs.
2. Pair and start a match. Leave the connection up beyond the first 10-second monitor tick; confirm no routine startup rebind occurs.
3. Test a brief Wi-Fi interruption that returns with the **same** source IPv4/interface. Confirm loss is detected and recovery retries occur. Also test loss of an unrelated Wi-Fi Network. DNS/IPv6/RSSI changes alone should not reconnect a healthy IPv4 socket.
4. If DHCP changes the local address or the interface is recreated with a different index, re-pair. This release deliberately does not claim transparent mid-match migration to a different source endpoint; the other phone still knows the old endpoint.
5. Check IPv4/IPv6 Internet passthrough where available, cancellation during recovery, and stop/reconnect after a failed startup. Verify diagnostics export and manual goal/full-time markers remain usable.
6. Compare sessions on the same phones and network. Correlate jitter timestamps with local packet processing, receive/queue timing, losses, and rebind logs. A passing host suite does not establish that real game jitter has disappeared.

## References checked

- [Android NetworkCallback](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback): callbacks provide ordered link-property events; synchronous queries inside callback bodies can race.
- [Android Network.bindSocket](https://developer.android.com/reference/android/net/Network#bindSocket(java.io.FileDescriptor)): requires an unconnected socket.
- [Android kernel timestamping documentation](https://android.googlesource.com/kernel/common.git/+/refs/tags/ASB-2020-09-05_4.14-stable/Documentation/networking/timestamping.txt): TSONLY returns timestamps with empty payloads and reduces receive-budget usage.
- [Linux socket manual](https://man7.org/linux/man-pages/man7/socket.7.html), [UDP manual](https://man7.org/linux/man-pages/man7/udp.7.html), and [send manual](https://man7.org/linux/man-pages/man2/send.2.html): asynchronous errors, extended error queues, and datagram send semantics.
